Module 01 Why Unit Testing Matters

A unit test is a small, automated piece of code that checks whether one isolated piece of your program — usually a single method — behaves the way you expect, without needing a human to click through the app. You run it, it passes or fails, and it takes milliseconds.

Without tests, the only way to know your code works is to run the whole application and manually poke at it. That's slow, it doesn't scale, and it doesn't stop you from breaking something in InventoryManager six weeks from now while fixing an unrelated bug in DialogueSystem. A good test suite catches that regression in under a second, before it ever reaches a player.

Tests are usually organized as a pyramid:

  • Unit tests — fast, numerous, test one class/method in isolation. This course.
  • Integration tests — check that multiple units work together (e.g. a service talking to a real database).
  • End-to-end tests — drive the whole application like a user would. Slow, brittle, few of them.

You want many unit tests, some integration tests, and few end-to-end tests — because unit tests are the cheapest to write, the fastest to run, and the easiest to pinpoint a failure in.

Key idea: a test is a specification you can execute. It doesn't just check code — it documents what the code is supposed to do, in a form that can never go stale, because it fails the moment reality disagrees with it.
Try it yourself: think of one method in a project you've written (a damage calculation, a score formula, a save-file parser). Write down, in plain English, three things that must always be true about its output. Those three sentences are your first three test cases — you'll turn them into real code in Module 3.
Module 02 Setting Up JUnit 5

JUnit 5 (also called "JUnit Jupiter") is the current standard testing framework for Java. It's made of three parts you don't need to memorize — Jupiter (the API you write tests against), the Platform (runs tests), and Vintage (runs old JUnit 3/4 tests) — but you do need to add the dependency to your build tool.

Maven — add this to pom.xml:

<!-- pom.xml -->
<dependency>
  <groupId>org.junit.jupiter</groupId>
  <artifactId>junit-jupiter</artifactId>
  <version>5.10.2</version>
  <scope>test</scope>
</dependency>

Gradle — add this to build.gradle:

// build.gradle
testImplementation('org.junit.jupiter:junit-jupiter:5.10.2')
test { useJUnitPlatform() }

Project layout matters: Maven and Gradle both expect production code under src/main/java and tests under src/test/java, mirroring the same package structure. A class com.avgjude.forge.CombatEngine gets its tests in com.avgjude.forge.CombatEngineTest — same package, different source root. This lets tests access package-private members while staying physically separate from shipped code.

Watch out: if `mvn test` or `gradle test` reports "0 tests run" even though you have test files, it's almost always one of two things — the dependency scope isn't test, or the test class/method naming doesn't match what the build tool's test runner looks for (Maven Surefire expects classes ending in Test, Tests, or TestCase by default).
Try it yourself: create a fresh Maven or Gradle project, add the JUnit 5 dependency above, and create an empty CalculatorTest class with one empty @Test method. Run the build and confirm you see "1 test run, 0 failures" before moving on.
Module 03 Anatomy of a Test

Every test follows the same three-part shape, called Arrange, Act, Assert (AAA): set up the data you need, call the method you're testing, then check the result. Here's a full example testing a simple damage calculator:

import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class DamageCalculatorTest {

    @Test
    void criticalHit_doublesBaseDamage() {
        // Arrange
        DamageCalculator calc = new DamageCalculator();
        int baseDamage = 20;

        // Act
        int result = calc.applyCritical(baseDamage);

        // Assert
        assertEquals(40, result);
    }
}

Three rules make this a valid JUnit 5 test: the class doesn't need to extend anything, the method is annotated @Test, and it returns void. JUnit finds every @Test-annotated method via reflection, runs each one in its own fresh instance of the test class (so tests can't leak state between each other), and reports pass/fail based on whether any assertion or exception was thrown.

Name your test methods to describe the behavior, not the implementation — criticalHit_doublesBaseDamage tells you what broke just from the test report, without opening the file. A common convention is methodOrScenario_condition_expectedResult.

Key idea: a test class is instantiated fresh for every single test method. That means you can't accidentally rely on one test running before another to set up shared state — and if you find yourself wanting that, it's usually a sign you need @BeforeEach (Module 5), not test ordering.
Try it yourself: write a StringUtils class with one method, reverse(String s). Write three tests: reversing a normal word, reversing an empty string, and reversing a single character. Watch all three go green.
Module 04 Assertions Deep Dive

Assertions are how a test actually decides pass or fail. org.junit.jupiter.api.Assertions gives you a large static toolbox:

assertEquals(expected, actual);
assertEquals(expected, actual, "failure message");
assertNotEquals(unexpected, actual);
assertTrue(condition);
assertFalse(condition);
assertNull(value);
assertNotNull(value);
assertSame(expectedRef, actualRef);   // same object identity
assertArrayEquals(expectedArr, actualArr);
assertIterableEquals(expectedList, actualList);

Two assertions deserve special attention. assertAll() groups several checks so that all of them run and report their failures together, instead of stopping at the first failure:

@Test
void newCharacter_hasCorrectDefaults() {
    Character c = new Character("Rootwarden");
    assertAll("character defaults",
        () -> assertEquals(1, c.getLevel()),
        () -> assertEquals(100, c.getHealth()),
        () -> assertTrue(c.isAlive())
    );
}

assertThrows() is how you test that code correctly rejects bad input by throwing an exception:

@Test
void withdraw_moreThanBalance_throwsException() {
    Account acc = new Account(50);
    var ex = assertThrows(InsufficientFundsException.class,
        () -> acc.withdraw(100));
    assertEquals("Insufficient funds", ex.getMessage());
}

Note the argument order for assertEquals is expected, then actual — get this backwards and your failure messages will read "expected X but was Y" with X and Y swapped, which wastes real debugging time.

Beyond built-in assertions: many teams add AssertJ (assertThat(result).isEqualTo(40)) for fluent, chainable assertions with much better failure messages on collections and objects. It's a separate library but drops in alongside JUnit 5 with zero conflict.
Try it yourself: rewrite Module 3's criticalHit_doublesBaseDamage test using assertAll to also check that a non-critical hit does not double damage, and that negative base damage throws an IllegalArgumentException.
Module 05 Test Lifecycle Annotations

Most test classes need the same setup repeated before every test — creating an object under test, resetting a database connection, and so on. JUnit 5 gives you four lifecycle hooks:

class InventoryTest {

    private Inventory inventory;

    @BeforeAll
    static void setupOnce() {
        // runs ONCE before all tests in this class (must be static)
    }

    @BeforeEach
    void setup() {
        // runs before EVERY test — fresh state, no leakage
        inventory = new Inventory(20);
    }

    @Test
    void addItem_increasesCount() {
        inventory.add("Iron Sword");
        assertEquals(1, inventory.count());
    }

    @AfterEach
    void tearDown() {
        // runs after EVERY test — close resources, reset mocks
    }

    @AfterAll
    static void tearDownOnce() {
        // runs ONCE after all tests (must be static)
    }
}

@BeforeEach/@AfterEach are by far the most used — they keep every test starting from clean, identical state, which is what makes tests trustworthy and order-independent. @BeforeAll/@AfterAll must be static (unless you change the test instance lifecycle) and are for genuinely expensive one-time setup, like starting an in-memory database.

You can also organize related tests into nested groups with @Nested, which is useful for testing the same class under different starting conditions:

class AccountTest {

    @Nested
    class WhenBalanceIsZero {
        private Account acc;
        @BeforeEach void setup() { acc = new Account(0); }

        @Test
        void withdraw_anyAmount_throws() {
            assertThrows(InsufficientFundsException.class, () -> acc.withdraw(1));
        }
    }

    @Nested
    class WhenBalanceIsPositive {
        private Account acc;
        @BeforeEach void setup() { acc = new Account(100); }

        @Test
        void withdraw_lessThanBalance_succeeds() {
            acc.withdraw(30);
            assertEquals(70, acc.getBalance());
        }
    }
}
Watch out: never share mutable state between tests through a static or instance field set up once in @BeforeAll if any test modifies it — the next test that runs will silently start from a polluted state, and you'll get "flaky" tests that fail depending on run order.
Try it yourself: take your Inventory class and write nested test groups: WhenInventoryIsEmpty and WhenInventoryIsFull, each with its own @BeforeEach and at least two tests appropriate to that state.
Module 06 Display Names, Tags & Disabling Tests

Method names are constrained by Java syntax, but test reports don't have to be. @DisplayName lets you write a human-readable description that shows up in IDE and CI test reports instead of the raw method name:

@Test
@DisplayName("Critical hits should deal exactly double base damage")
void criticalHit_doublesBaseDamage() { /* ... */ }

@Tag lets you group tests across classes so you can run a subset — for example, running only fast unit tests in a pre-commit hook while running slow integration tests separately in CI:

@Test
@Tag("slow")
void fullSaveLoadRoundTrip_preservesAllData() { /* ... */ }

Maven Surefire and Gradle can both be configured to include or exclude tags at build time, so a developer's local build can skip the slow suite while the CI pipeline runs everything.

Sometimes a test needs to be temporarily switched off — a feature isn't implemented yet, or a known bug is being tracked separately. @Disabled does that visibly, instead of commenting the test out (which hides it from reports entirely):

@Test
@Disabled("Blocked on JIRA-482 — status effect stacking not yet implemented")
void poisonStacksThreeTimes_dealsTripleDamagePerTick() { /* ... */ }
Watch out: @Disabled tests still show up in the report as "skipped," which is the point — a commented-out test is invisible and gets forgotten forever. Always include a reason string so future-you (or a teammate) knows why it's off and when it's safe to re-enable.
Try it yourself: add @DisplayName to every test you've written so far, tag your slowest test "slow", and disable one test with a reason explaining what's blocking it.
Module 07 Parameterized Tests

Copy-pasting the same test five times with different numbers is a maintenance trap. @ParameterizedTest runs one test method against many inputs, reporting each as its own pass/fail. The simplest source is @ValueSource:

@ParameterizedTest
@ValueSource(ints = {1, 2, 4, 8, 16})
void isPowerOfTwo_returnsTrue(int value) {
    assertTrue(MathUtils.isPowerOfTwo(value));
}

When you need multiple related inputs per run — like an input and its expected output — use @CsvSource:

@ParameterizedTest
@CsvSource({
    "20, false, 20",
    "20, true, 40",
    "0, true, 0"
})
void applyCritical_computesExpectedDamage(int base, boolean isCrit, int expected) {
    DamageCalculator calc = new DamageCalculator();
    assertEquals(expected, calc.apply(base, isCrit));
}

For cases that don't fit neatly into a string (like custom objects), @MethodSource points to a static factory method that supplies a stream of arguments:

@ParameterizedTest
@MethodSource("characterProvider")
void newCharacter_startsAlive(Character c) {
    assertTrue(c.isAlive());
}

static Stream<Character> characterProvider() {
    return Stream.of(
        new Character("Rootwarden"),
        new Character("Voltcaller")
    );
}

There's also @EnumSource for iterating over every value of an enum, and @NullSource/@EmptySource for cheaply covering null/empty edge cases without a full CSV row.

Key idea: parameterized tests are how you turn "I should probably test some edge cases" into actually testing all of them — zero, negative numbers, max int, empty string, null — with almost no extra code per case.
Try it yourself: convert your Module 3 reverse() tests into a single @CsvSource-driven parameterized test covering at least five input/expected pairs, including an empty string and a palindrome.
Module 08 Testing Exceptions, Timeouts & Edge Cases

A method's "happy path" is only half the spec. What it does when given garbage input, or when it takes too long, is just as important — and JUnit 5 has dedicated tools for both.

You already saw assertThrows in Module 4. It returns the thrown exception so you can assert on its message or cause, which matters because "it threw an exception" is a much weaker guarantee than "it threw this specific exception with this message":

@Test
void parseLevel_negativeNumber_throwsWithClearMessage() {
    var ex = assertThrows(IllegalArgumentException.class,
        () -> LevelParser.parse("-5"));
    assertTrue(ex.getMessage().contains("must be positive"));
}

To guarantee a method doesn't hang forever, assertTimeout fails the test if the code takes longer than the given duration:

@Test
void pathfinding_onLargeMap_completesQuickly() {
    assertTimeout(Duration.ofMillis(200), () -> {
        pathfinder.findPath(largeMap, start, end);
    });
}

assertTimeout lets the code finish running even if it exceeds the limit (it just fails afterward). If you need it to be forcibly interrupted the instant it goes over — for something that might infinite-loop — use assertTimeoutPreemptively instead, which runs the code on a separate thread.

Beyond exceptions and timing, always deliberately test boundary values: zero, negative numbers, empty collections, the maximum allowed value, one-past-the-maximum, null. Bugs cluster at boundaries far more than in the middle of the "normal" range.

Watch out: don't wrap an entire test body in a broad try/catch that swallows exceptions to "make the test pass" — an uncaught exception failing a test is correct and informative behavior. If you expect an exception, assert on it explicitly with assertThrows.
Try it yourself: for a method you've already tested, add one test for the zero/empty boundary, one for a negative or invalid input using assertThrows, and one assertTimeout guarding against unexpectedly slow behavior.
Module 09 Mocking with Mockito

A "unit" test should test one unit — but real classes depend on other classes: a database, a network client, a file system. You don't want your OrderService test to actually hit a database. Mockito lets you replace a dependency with a fake object you fully control.

Add it alongside JUnit 5:

// Maven
<dependency>
  <groupId>org.mockito</groupId>
  <artifactId>mockito-junit-jupiter</artifactId>
  <version>5.11.0</version>
  <scope>test</scope>
</dependency>

Here's a service that depends on a repository interface, tested with a mock in place of the real database-backed implementation:

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock
    private OrderRepository repository;

    @InjectMocks
    private OrderService service;

    @Test
    void placeOrder_savesOrderAndReturnsConfirmation() {
        // Arrange — tell the mock what to return when called
        when(repository.save(any(Order.class)))
            .thenReturn(new Order("ORD-1001"));

        // Act
        Confirmation result = service.placeOrder(new Cart());

        // Assert on the result...
        assertEquals("ORD-1001", result.orderId());

        // ...and verify the interaction actually happened
        verify(repository, times(1)).save(any(Order.class));
    }
}

@Mock creates the fake, @InjectMocks creates the real OrderService and automatically wires the mock into its constructor. when(...).thenReturn(...) stubs behavior; verify(...) checks that a method was actually called, which matters for methods that don't return anything (like sending an email or writing a log).

An argument captor lets you inspect exactly what was passed into a mocked call, useful when you care about the details of an interaction, not just that it happened:

@Test
void placeOrder_savesOrderWithCorrectTotal() {
    ArgumentCaptor<Order> captor = ArgumentCaptor.forClass(Order.class);
    service.placeOrder(cartWithTotal(59.99));

    verify(repository).save(captor.capture());
    assertEquals(59.99, captor.getValue().getTotal());
}
Watch out: mocking works cleanly when your class depends on interfaces, not concrete classes reached directly (e.g. new FileWriter(...) inside a method). If a class is hard to test, that's frequently a design smell pointing at missing dependency injection — see Module 10.
Try it yourself: create a NotificationService that depends on an EmailClient interface. Mock the client, verify send() is called exactly once with the correct recipient when a user levels up, and never called if the level didn't change.
Module 10 Test Doubles & Designing for Testability

"Mock" gets used loosely, but there are actually several distinct kinds of test double (a general term for any stand-in object used in a test), each suited to a different job:

  • Dummy — passed around to satisfy a parameter list but never actually used.
  • Stub — returns canned answers to calls made during the test, nothing more (Mockito's when().thenReturn()).
  • Fake — a real, working, simplified implementation — e.g. an in-memory HashMap-backed repository standing in for a real database.
  • Mock — a stub that also records how it was called, so the test can verify() interactions.
  • Spy — wraps a real object, letting most calls through to the real implementation while selectively overriding or verifying specific ones.

None of this works if a class hardcodes its dependencies. Compare:

// Hard to test — constructs its own dependency internally
class ReportGenerator {
    void generate() {
        Database db = new PostgresDatabase("prod-url"); // can't swap this in a test
        // ...
    }
}

// Testable — dependency is injected from outside
class ReportGenerator {
    private final Database db;
    ReportGenerator(Database db) { this.db = db; } // constructor injection

    void generate() {
        db.query("..."); // can be a real DB in prod, a mock in tests
    }
}

This is dependency injection: a class receives its collaborators from the outside (usually via constructor) instead of creating them itself. It's the single biggest design change that makes code unit-testable, and it's why "hard to test" and "tightly coupled" are usually the same complaint.

Key idea: if writing a test for a class feels painful — you need to spin up a real database, a real network call, a real file on disk — that pain is valuable feedback about the class's design, not just an annoyance to work around.
Try it yourself: find a class in one of your own projects that directly instantiates a dependency (a file reader, a network client, a `new Random()`). Refactor it to accept that dependency through its constructor instead, then write a test using a fake or mock in place of the real thing.
Module 11 Code Coverage & Its Limits

JaCoCo is the standard Java code coverage tool — it instruments your compiled code and reports what percentage of lines, branches, and methods were actually executed while your tests ran. Add the plugin to Maven:

<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <version>0.8.11</version>
  <executions>
    <execution>
      <goals><goal>prepare-agent</goal></goals>
    </execution>
    <execution>
      <id>report</id>
      <phase>test</phase>
      <goals><goal>report</goal></goals>
    </execution>
  </executions>
</plugin>

Running mvn test then produces an HTML report under target/site/jacoco/index.html showing exactly which lines and branches were and weren't hit.

But here's the trap: 100% coverage does not mean your code is correct. Coverage only proves a line ran during a test — not that the test checked the right thing. This "test" gets 100% coverage while asserting nothing:

@Test
void uselessTest() {
    calculator.applyCritical(20); // executes the line... proves nothing
    // no assertion at all — this test can never fail
}

Treat coverage as a gap finder, not a quality score: a low number on a critical class tells you exactly where to write more tests. A high number tells you nothing about whether those tests are any good. Aim for meaningful coverage of business logic and edge cases, not a percentage on a dashboard.

Going further — mutation testing: tools like PIT (pitest) take this further by automatically introducing small bugs ("mutants") into your compiled code — flipping a > to >=, for example — and checking whether your test suite catches each one. A test suite that "kills" a high percentage of mutants is actually verifying behavior, not just executing lines.
Try it yourself: run JaCoCo on a class you've already tested. Find one uncovered branch (usually an edge case or error path you skipped) and write the test that covers it.
Module 12 Test-Driven Development (Red–Green–Refactor)

So far you've written tests for code that already exists. Test-Driven Development (TDD) flips the order: write the failing test first, then write just enough code to make it pass, then clean up. The cycle repeats in three steps:

  1. Red — write a test for behavior that doesn't exist yet. Run it. Watch it fail (it should fail to compile or fail the assertion — if it passes, something's wrong with the test).
  2. Green — write the smallest, dumbest amount of code that makes the test pass. Don't gold-plate it yet.
  3. Refactor — now that a passing test protects you, clean up the implementation: remove duplication, improve names, extract methods. Re-run the test after every change to confirm it still passes.

Worked example — building a FizzBuzz-style level-title generator one behavior at a time:

// RED — this fails because LevelTitle doesn't exist yet
@Test
void level1_isTitledNovice() {
    assertEquals("Novice", LevelTitle.forLevel(1));
}

// GREEN — simplest possible implementation
class LevelTitle {
    static String forLevel(int level) {
        return "Novice"; // hardcoded — but the test passes, and that's the point right now
    }
}

// RED again — add the next behavior
@Test
void level10_isTitledVeteran() {
    assertEquals("Veteran", LevelTitle.forLevel(10));
}

// GREEN — now the hardcoded value has to go
static String forLevel(int level) {
    if (level >= 10) return "Veteran";
    return "Novice";
}
// REFACTOR — once more titles exist, extract to a sorted table/lookup

The discipline here isn't "write tests" — it's never writing production code without a failing test demanding it. That constraint naturally keeps you from building things you don't need yet, and it means the test suite grows in lockstep with the code instead of being bolted on afterward (or never).

Watch out: TDD is a discipline, not a religion — plenty of excellent engineers write code first and backfill tests, especially for exploratory or throwaway work. Use TDD where it earns its keep: complex business logic, algorithms, anything with many edge cases — not for a one-line getter.
Try it yourself — a small kata: using strict Red-Green-Refactor, build a PasswordValidator.isValid(String) that requires: at least 8 characters, at least one digit, at least one uppercase letter. Write one failing test per rule, in that order, never writing validation logic that isn't demanded by a test you just watched fail.
Module 13 Test Organization at Scale

A handful of tests are easy to keep straight. Hundreds require conventions. A few that pay off immediately:

  • One test class per production class, same package, mirrored under src/test/java — CombatEngine → CombatEngineTest.
  • Group by scenario with @Nested (Module 5) rather than one flat class with fifty methods.
  • One assertion concept per test. A test named withdraw_succeeds that also happens to check three unrelated things is really three tests wearing a trench coat — split it up so a failure tells you precisely what broke.
  • Shared setup goes in @BeforeEach or a small test-fixture helper class, not copy-pasted across twenty methods.
  • Use @Tag (Module 6) to separate fast unit tests from slower integration tests, and configure your build to run them as separate suites.

For very large projects, JUnit 5's @Suite (from the junit-platform-suite artifact) lets you explicitly bundle multiple test classes or whole packages into a named suite that can be run as one unit:

@Suite
@SelectPackages("com.avgjude.forge.combat")
@IncludeTags("fast")
class FastCombatSuite { }
Key idea: a well-organized test suite is documentation. A new contributor should be able to open CombatEngineTest and understand every rule the combat system enforces just from reading the @DisplayNames, top to bottom, without reading a single line of implementation.
Try it yourself: take every test class you've written in this course and audit it against the list above — split any test that checks more than one concept, and move duplicated setup into @BeforeEach.
Module 14 Best Practices & Common Anti-Patterns

Good unit tests follow the FIRST principles:

  • Fast — milliseconds. A slow suite gets run less often, which defeats the purpose.
  • Independent — no test depends on another test running first, or on shared mutable state.
  • Repeatable — same result every time, on any machine, in any order. No dependence on system clock, network, or random seeds unless explicitly controlled.
  • Self-validating — pass or fail, no human reading console output to decide.
  • Timely — written close to when the production code is written, ideally before (Module 12), not months later as an afterthought.

Common anti-patterns to avoid:

  • The Liar — a test that passes but doesn't actually verify the behavior its name claims to (like the empty-assertion example in Module 11).
  • Flaky tests — pass sometimes, fail other times, usually from relying on timing, thread ordering, real network calls, or System.currentTimeMillis()/real random values without a fixed seed. A flaky test that gets "just re-run it" instead of fixed will eventually be ignored entirely, including when it's catching a real bug.
  • Testing implementation, not behavior — asserting on private internal state or exact call counts of things that don't matter to the outcome, which breaks the test the moment you refactor without changing behavior.
  • The Giant — a single test method hundreds of lines long checking a dozen things. Split it.
  • Excessive mocking — mocking every single collaborator, several layers deep, until the test only proves that your mocks do what you told them to do, not that the real system works.
Key idea: test behavior — inputs and outputs, observable effects — not implementation details. A test suite that breaks every time you rename a private method or reorder internal steps, without any actual bug, is actively costing you velocity instead of protecting it.
Try it yourself: pick your longest test method from this course and check it against FIRST. If it's testing more than one behavior, split it. If it depends on real time or randomness, inject a fixed clock or seeded random generator instead.
Module 15 Running Tests in CI (GitHub Actions)

Tests that only run on your own machine still leave room for "works for me." The payoff comes from running the full suite automatically on every push, so a broken build is caught before it reaches anyone else. Here's a minimal GitHub Actions workflow for a Maven project:

# .github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up JDK 21
        uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: maven
      - name: Run tests
        run: mvn -B test
      - name: Upload coverage report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: jacoco-report
          path: target/site/jacoco

Every push and every pull request triggers this: checkout the code, install the right JDK, run mvn test, and archive the coverage report as a downloadable artifact regardless of pass/fail (if: always()) so you can inspect what happened even on a red build. Maven's Surefire plugin exits non-zero on any test failure, which is what makes GitHub Actions mark the whole job as failed — no extra configuration needed.

A typical team policy: pull requests can't merge unless this workflow is green. That single rule is what actually makes a test suite valuable at scale — tests that people can skip running are tests that eventually get skipped.

Key idea: a test suite only protects a codebase if it's actually run — consistently, by everyone, before code merges. Automating that removes it from being a matter of discipline and makes it a property of the pipeline.
Try it yourself: add the workflow above to a real GitHub repo of yours with a JUnit 5 test suite, push a commit, and confirm the Actions tab shows a green check. Then deliberately break a test and push again — confirm it shows red.
Module 16 Capstone: Test a Full Class from Scratch

Everything in this course, applied at once. Build and fully test a TournamentBracket class using strict TDD:

  1. It's constructed with a list of player names (must have a power-of-two count, or it throws IllegalArgumentException — test this first).
  2. recordWin(String winner, String loser) advances the winner to the next round.
  3. recordWin with a player not currently in the active round throws IllegalStateException.
  4. getChampion() returns the sole remaining player after all rounds complete, or throws if the tournament isn't finished.
  5. It depends on a MatchLogger interface (injected via constructor) that gets notified of every recorded win — mock this and verify it's called with correct arguments.

Requirements for your test suite:

  • Use @BeforeEach for shared bracket setup.
  • Use @Nested to separate "invalid construction," "mid-tournament," and "final round" scenarios.
  • Use at least one @ParameterizedTest (e.g. testing several invalid player-count values at once).
  • Use assertThrows for both exception cases.
  • Mock MatchLogger with Mockito and verify() it's called correctly.
  • Run JaCoCo and get meaningful (not just numeric) coverage of every branch, including the error paths.
Self-check: before you consider this done, delete your implementation of one method, leave only the tests, and rebuild it from red to green using only what the failing tests tell you. If you can do that cleanly, your tests are actually specifying the behavior — which was the whole point of Module 1.
When you're done: you've now covered the same ground a mid-level Java role expects for testing competency — JUnit 5 fundamentals, Mockito, parameterized and exception testing, coverage tooling, TDD, and CI integration. From here, the fastest way to get better is to go add tests to a real, untested class in one of your own projects.
